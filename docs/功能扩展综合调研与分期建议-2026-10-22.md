# 鲲穹文件传输功能扩展综合调研与分期建议

调研日期：2026-10-22  
需求范围：同时覆盖多人材料收集、对外交付、企业团队三类场景  
定位：产品方向建议及候选范围，不是开发工期或市场需求承诺

## 结论

建议采用 GPT 的收集流程作为一条主线，吸收 DS 的自定义字段、提交人自助修改、规则归档、品牌入口和集成建议，同时补上交付回执、项目组织两条线。三类场景都做，但按共同基础和依赖顺序分批上线。

最值得投入的核心能力是：**让发起者明确知道谁没交、缺什么、是否合格；让交付者明确知道谁确认收到；让团队能按项目找到资源和责任人。**

首个阶段建议包含五个产品模块，分三次小版本交付：

1. 收集模板、自定义字段和材料清单
2. 应交名单、缺件进度和定向催办
3. 提交人自助修改、审核和退回补交
4. 交付事件记录、主动收件确认和未确认名单
5. 团队项目分组、标签和基础品牌展示

规则命名与结构化打包并入收集模块；进度看板并入名单管理；按人追踪与主动回执一起设计。它们不需要分别做成独立的大功能。

固定链接替换、版本记录、误删恢复、固定团队收件入口排在第二阶段。高级水印、审计导出、Webhook、AI 和按次付费依据客户使用和成本数据再进入后续阶段。

## 调研方法与证据边界

- 核对当前仓库的使用手册、收集与分享接口、公开页面、团队页面、通知设置及打包实现。
- 本轮实际读取 Content Snare、FileInvite、MASV、Filemail、Nextcloud 和文叔叔官方公开页面。关键功能证据与链接见文末。
- Content Snare 的资料补充了前轮报告没有直接核实的自动催办、逐项审核和退回修改证据；FileInvite 补充了清单、多人进度、命名归档和团队协作证据。
- 搜索工具和部分站点访问受限：Agent Reach / mcporter 命令不可用，AutoGLM 本地令牌服务未运行，Jina 阅读请求失败；因此通过直接读取官方公开页面完成核验。Google 搜索未取得可用结果，Bing 未提供足够结果。Dropbox 连接超时，DocSend 返回 403，坚果云页面未返回可用正文，均不据此判断功能缺失或套餐。
- 未实测竞品付费功能，未完成独立用户评论样本、客户访谈或本产品行为数据分析。官方案例中的节省时间、转化率和满意度数据不作为鲲穹的效果预测。
- 下列优先级和复杂度属于结合代码和产品流程的判断；竞品公开提供某功能，只能证明产品形态存在，不能证明鲲穹用户一定需要或愿意付费。

| 草稿和自助修改 | 已有未完成上传的暂停、恢复；成功后可以再提交一份 | 跨会话业务草稿、查看自己的既有材料、按材料项替换和补交，不等于上传断点恢复 |

## 合并两份建议后的优先级

P0 为首阶段，P1 为第二阶段，P2 为取得具体客户或使用证据后的候选。首阶段分批交付，并不表示下表全部能力必须一次发布。复杂度包含权限和数据变更，只用于相对比较。

| 优先级 | 功能 | 建议范围及判断 | 相对复杂度 |
| --- | --- | --- | --- |
| P0 | 模板＋自定义字段＋材料清单 | 文本、下拉字段，材料项必交/选交、数量和格式，模板保存与复制；提供样例说明。作为收集基础 | 中 |
| P0 | 名单进度＋针对性催办 | 导入应交名单，展示未交、缺件、待审核、已通过；先支持导出与复制催办，再接已有可用通知渠道 | 中至高 |

| P0，随收集交付 | 规则命名＋结构化打包 | 利用字段生成目录；保留原文件名；选择最终或已通过材料。先做下载时整理 | 中 |
| P0 | 交付反馈＋主动确认收到 | 按收件人展示访问事件、下载事件和主动确认；身份未知明确标注；不默认追踪阅读时长 | 中至高 |

| P1 | 企业 IM 与提醒规则 | 有明确渠道后选一种；截止前提醒、退回补交通知和日报汇总，控制频率 | 中至高 |
| P1/P2 | 仅预览＋身份水印 | 文件类型和预览能力先定范围；服务端限制原件下载；水印与访问身份关联 | 高 |
| P1/P2 | 审计导出＋更细访问范围 | 先定义需审计的业务事件、保留期与导出权限；组织、域名白名单依据客户需求增加 | 中至高 |

| 商业试验 | 按次大文件包 | 适合低频发送者；先确认带宽、留存、重试下载和支付售后成本，再小范围测试 | 中至高 |

## 首阶段怎样兼顾三类用户

### 第一批：用户立刻看得见的提升

- 收集：任务复制、模板、自定义字段、逐项材料要求、样例与缺项提示。
- 交付：主动“确认收到”、事件时间线和未确认名单；明确对应收件人和分享版本。
- 团队：项目分组、标签、筛选和基础品牌展示。
- 整理：按字段生成下载目录和文件名；保留原名映射。

这一批主要解决重复设置、提交信息不全、交付无反馈和团队难查找。先统一字段与事件记录方式，减少后续返工。

### 第二批：收集从“收到文件”变成“知道是否收齐”

- 名单导入、稳定身份关联、已交/未交/缺件状态。
- 提交者个人查看入口、业务草稿、自助修改。
- 根据未完成状态选择催办对象；完成后停止提醒。
- 把现有统计升级为任务状态汇总，按异常状态筛选；自动刷新可后加，不先开发复杂实时图表。

### 第三批：明确材料收集结果

- 人工通过、退回原因、按材料项补交、版本或轮次留痕。
- 通过后的材料锁定，后续变更重新审核。
- 打包与导出支持只选已通过或最终材料。
- 任务负责人和基础处理记录；跨成员审核需要配套服务端权限。

三批合起来构成首阶段。未核定团队人力、目标并发和数据迁移范围前，不给出精确人日或固定周数。

## 比两份清单更值得补充的方向

### 1. 周期收集和一键发起下一期

适合月报、报销、项目周资料和周期素材。先做“复制任务并调整截止时间”，再做按周或按月生成新任务。上一期已提交不能误算为本期完成；每期要求保留快照。

它比泛化 AI 更贴近重复使用和留存。优先级建议 P1；一键复制可随 P0 模板上线。

### 2. 材料样例和提交前规则检查

每个材料项可附示例、命名说明和常见错误。先基于确定规则检查材料是否齐全、数量是否符合、格式与已知规范是否匹配；内容清晰度、证件有效性等需要另行评估。

当前已有格式和单文件大小校验，增量是逐材料项的要求与说明。可随 P0 模板加入，降低反复退回的概率。

### 3. 下载前整理，而非立刻建设复杂存储路由

先在打包时提供“按人 / 按材料 / 按项目”组织，支持原名与规范名称映射、重名处理、最新材料选择。待明确需要自动进入业务系统，再接云盘或 Webhook。

这样可直接复用现有打包和 Excel 导出，也让“自动整理”的价值能被用户立即验证。

### 4. 负责人交接和通知汇总

团队长期任务需要在成员离开时继续运转。为项目和收集任务设置负责人、协作人和交接规则；通知支持重要事件即时提醒、其他事件汇总。

现有账号收集管理接口限定任务所有者，完整交接不是单纯增加负责人字段，需要一起调整权限。建议 P1，与固定团队入口配套。

## 关键规则应在开发前一并确定

这些约束直接影响所推荐功能的可信度、工作量和存储成本。

1. **身份与匿名**：公开匿名收集继续保留；名单模式用稳定人员标识关联。姓名不能作为身份凭据。专属链接证明持有链接，若要声称“本人确认”，需要账号或额外验证。提交者只能查看自己的材料。
2. **三套状态分开**：安全扫描、提交完整度、业务审核分别记录；已提交不等于已收齐或已通过。
3. **变更与留痕**：模板、任务要求留快照；通过的材料被修改后重新审核。匿名自助修改使用独立的个人权限凭据，不能凭姓名或公开提交编号编辑。
4. **回执与事件**：访问、下载事件和主动确认分别统计；服务端下载事件不能保证对方已经读完或成功保存。回执绑定版本，更新文件后旧版确认不能自动算新版已确认。
5. **提醒**：仅催未完成对象，发送前重查状态，控制频率。当前绑定手机号不代表已接入短信；可先复用站内和邮件，IM 根据实际渠道接入。
6. **原链接替换**：新文件安全检查通过后切换；已有下载请求保持其开始时的版本；保留访问策略并明确旧版本空间占用。
7. **回收站**：区分手动删除、过期关闭与物理清理。恢复不能自动重新开放旧链接；实际保留的文件继续计算空间。现有删除路径会直接移除文件目录，需要改生命周期。
8. **仅预览与水印**：仅隐藏下载按钮不构成权限控制；水印不能承诺阻止截图或拍照。明确覆盖 PDF、图片还是 Office，再估算实现。
9. **固定入口**：入口地址长期有效与上传文件永久保存是两回事，仍要明确每批文件的生命周期。
10. **AI 与集成**：处理权限和原文件权限一致；外部 AI 调用前提供明确选择。Webhook 需签名、幂等、失败重试和投递记录，避免按“一个回调地址”估算。

## 商业化建议

建议保留容量权益，同时增加流程价值的区分，不直接照搬国外价格。

| 档位方向 | 可保留或提供的价值 |
| --- | --- |
| 基础使用 | 现有基础收发、小规模模板和清单、基础主动回执；让收件与提交过程顺畅 |
| 个人效率 | 更多活跃任务、规则整理、周期复用、交付统计、版本与恢复额度 |
| 团队 | 项目管理、批量名单、自动催办、协作审核、固定品牌入口、交接 |
| 企业增值 | 更细访问范围、业务审计导出、SSO 或集成、Webhook/API 与明确服务支持 |
| 低频用户试验 | 按次大文件包；依据流量和留存成本定额与有效期 |

与其先把所有能力都限制成付费，不如用基础模板、回执和顺畅提交建立使用习惯，把规模化处理和多人协作放在更高档。具体权益仍需结合当前套餐和客户试用结果评审。

## 需求验证与成功指标

三条线分别找近期真实完成过任务的用户，小样本先发现问题；扩大样本后再做更强结论。记录上线前基线，不预设提升百分比。

| 场景 | 需要核对的问题 | 观察指标 |
| --- | --- | --- |
| 材料收集 | 最近一次到底花时间在催人、缺件、重命名还是退回？是否有现成名单？ | 首次提交齐全率、按期收齐率、从发起到全部通过时长、人工催办次数、模板复用率 |
| 对外交付 | 是否经常追问收到没有？是否反复换版本和重发链接？ | 主动确认率、人工追问次数、交付后重复发链频率、版本功能重复使用 |
| 企业团队 | 文件最常按客户、项目还是部门查？是否出现任务无人接管？ | 项目归档使用率、查找任务耗时、多人协作任务数、团队周留存、付费试用转化 |

如果真实数据表明发送远多于收集，应增加交付反馈和原链接替换的资源；若团队高频收资料，应先完成名单、审核与交接。全部方向可以保留，但持续投入依据真实使用调整。
