# 鲲穹文件传输 · 新功能调研与首批建议

> 调研日期：2026-10-22  
> 调研方式：现有代码与页面盘点、公开竞品形态对照、团队/企业使用场景推演  
> 说明：本文是选题建议，不是最终 PRD。工作量按现有架构估算，含开发自测，不含视觉设计、外部资质审批和真实客户联调等待。

---

## 0. 一页结论

### 建议首批做 3 个，企业 IM 通知作为可选第 4 个

| 顺序 | 功能 | 解决什么问题 | 建议套餐 | 预估工作量 |
|---|---|---|---|---|
| 1 | **分享访问数据看板** | 发送方不知道文件有没有被看到、被谁下载、什么时候下载 | 月卡会员及以上 | 6–8 人日 |
| 2 | **收集任务 2.0**：自定义字段 + 提交通知 + 模板库 | 收集到的信息不全，新提交没人知道，每次都要重新填要求 | 团队季卡及以上（基础版保留 3 个字段） | 9–12 人日 |
| 3 | **品牌分享页 + 二维码海报 + 自定义短链** | 分享页千篇一律，企业发给客户不够正式，线下传播不方便 | 月卡会员（简版）/团队季卡（完整品牌） | 8–10 人日 |
| 4（可选） | **企业 IM 通知**：企业微信 / 钉钉 / 飞书 | 团队不在站内，文件到了没人提醒，容易漏看 | 团队季卡及以上 | 8–11 人日 |

**合计：核心 3 个约 25–35 人日（含缓冲）；加 IM 通知约 35–45 人日。**  
按 1 名熟悉代码的全栈 + 0.5 名前端/测试估算，约 5–6 周可完成核心 3 个；单人开发顺延 1–2 周。

### 如果只做一件事

**先做「分享访问数据看板」。**  
理由：改动最小、上线最快、演示效果最直观；它把现在只有「已下载 N 次」的管理页，升级成「谁看过、谁下载、最近一次是什么时候」的交付反馈，能直接支撑会员版卖点。

### 如果做三件事

**分享数据 + 收集 2.0 + 品牌分享页。**  
这三个分别对应「发送方有反馈」「收集方有效率」「企业方有品牌感」，覆盖个人会员、团队、企业三类客户，且都复用现有上传、分享、收集、通知、套餐能力，不需要改存储架构。

### 暂不建议现在做

- **独立桌面/手机客户端**：投入大、维护成本高，当前 Web 端核心链路已完整，建议等首批功能验证后再评估。
- **网盘化永久存储 / 转存到我的空间**：会把「临时传输」做成「网盘」，涉及新的文件生命周期、配额、清理和版权策略，属于战略级选题，需单独立项。
- **全量 AI 文档问答**：模型成本、隐私合规、准确率都还不确定，建议先做小范围付费试点，不放进首批。
- **对象存储 / CDN 迁移**：当前量级不是瓶颈，等并发或带宽真正打满再上，避免过早增加运维复杂度。

### 需要领导拍板

1. 本季度优先目标是**会员转化**、**团队/企业签单**，还是**拉新**？
2. 首批做 **3 个**还是 **4 个**？如果团队客户更急，建议把「企业 IM 通知」提前。
3. 新功能是**全部计入现有套餐**，还是做**增值包/企业版专属**？
4. 访问日志是否允许记录 IP？保留 30 天、90 天还是 180 天？
5. AI 功能是否允许调用第三方模型？是否接受按次成本？

## 1. 现状盘点

### 1.1 已经具备的能力

| 域 | 现有能力 |
|---|---|
| **传输** | 分片上传、暂停/续传、取消、文件夹与批量选择、保留目录结构；单文件上限按套餐 2–20GB；ClamAV 安全检查；分享链接、二维码、4–6 位取件码、提取密码、有效期、下载次数、定向收件人（需登录且校验收件人）、企业专属链接、关闭/重开、管理口令；在线预览 PDF / Word / Excel / PPT / 图片 / 音视频 / 文本；打包下载、单文件下载、Range 下载 |
| **收集** | 匿名或登录提交、提交人名称、文件类型/单文件大小/截止时间/参与人数/任务数量限制、管理链接、提交回执、批量下载、单文件下载与预览、xlsx 提交清单、删除提交、团队专属收集链接 |

| **团队** | 创建团队、邀请成员、入团申请审批、成员角色（所有者/管理员/成员）、转让所有权、退出/解散、团队容量、团队资源列表、成员用量展示 |
| **后台** | 独立管理员会话、数据看板、资源管理、用户管理、系统配置、审计日志、清理、代登录 |
| **基础设施** | SEO 路由、sitemap、用户手册、较完整的接口/UI 回归脚本、Docker 部署、MySQL 元数据模式 |

### 1.2 目前明显的缺口

| 缺口 | 现状 | 影响 |
|---|---|---|
| **分享访问数据** | 只有累计 `downloadCount`，没有访问人数、访问时间、设备、单文件下载分布、趋势 | 发送方无法判断文件是否送达，销售/HR 无法跟进 |
| **收集任务信息不完整** | 提交页只有「提交人名称」，没有手机号、邮箱、备注、下拉选项等自定义字段 | 收集方还要线下补信息，效率低 |
| **收集提交通知缺失** | 新提交只落库，不主动提醒收集人；邮件/SMS 主要覆盖绑定与分享通知 | 收集人必须反复打开页面查看，容易错过截止 |
| **收集模板缺失** | 每次从空白表单开始填类型、大小、截止时间 | 新用户上手慢，场景化能力弱 |
| **品牌与传播能力弱** | 分享页是统一模板，没有 logo/封面/品牌色/自定义留言；二维码是白底方码 | 企业客户觉得不够正式，线下物料不好用 |
| **团队协作深度不足** | 团队资源是「单个分享/收集」的集合，没有共享文件夹、移动/复制、成员配额 | 团队版价值感偏弱，难卖更高客单 |
| **企业集成缺失** | 没有企微/钉钉/飞书通知，没有开放 API/Webhook | 难接入客户现有流程，企业采购缺理由 |
| **安全增值能力不足** | 有提取密码、定向收件人、病毒扫描；没有预览水印、手机号验证取件、DLP、团队级审计导出 | 法务/财务/教育等敏感场景不好卖 |
| **增长工具缺失** | 没有优惠券、兑换码、邀请返利、企业开票 | 拉新和成交缺少抓手 |
| **AI 能力空白** | 没有文档摘要、问答、OCR、自动分类 | 不影响主线，但是差异化机会 |

> 结论：核心传输与收集链路已经完整，当前缺的不是「能不能传」，而是**发送后的反馈、收集后的闭环、团队/企业的可管理性**。

## 2. 行业趋势：同类产品在往哪里走

1. **从「发链接」转向「交付闭环」**  
   公开产品普遍在传输之外补收集、回执、统计、审批。用户要的不只是「文件到了」，而是「对方收了没有、什么时候收的、还缺什么」。

2. **企业采购越来越看安全与可控**  
   定向访问、提取验证、水印、审计、权限、私有化部署，正在从加分项变成准入门槛。单纯「大文件不限速」很难支撑企业客单。

3. **协作入口向 IM 迁移**  
   企业微信、钉钉、飞书是团队日常入口。文件到了要在群里提醒，收集提交要能自动通知，否则用户不会天天打开独立网站。

4. **AI 从「生成噱头」转向「文档理解」**  
   真正有价值的是：收件人下载前先看摘要、问几个问题；收集方自动识别文件类型、缺失材料、重复提交。不是做一个聊天框就叫 AI。

5. **商业化从「卖空间」转向「卖能力」**  
   空间和流量越来越便宜，愿意付费的是：品牌定制、访问数据、团队权限、审计、API、加速、增值包。

> 对我们的含义：**不要和网盘拼容量，要把「传输 + 收集 + 团队协作」做成可管理、可追踪、可品牌化的交付工具。**

## 4. 首批三个功能的详细方案

### F1 分享访问数据看板

**用户故事**

> 销售把报价单发给客户后，想知道客户有没有打开、下载了几次、是不是转发给了别人。现在管理页只有一个「已下载 3 次」，看不出是谁、什么时候、用什么设备。

**功能清单（MVP）**

- 分享管理页新增「数据」区域：
  - 访问次数（PV）、访问人数（UV，按脱敏设备/IP 哈希去重）
  - 下载次数、下载人数、最近一次访问/下载时间
  - 近 7 天 / 30 天趋势（简单柱状图或折线图）
  - 设备分布：桌面 / 手机 / 平板 / 其他
  - 单文件下载次数排行（多文件分享时）
  - 最近 20 条访问记录：时间、设备、来源（链接/二维码/取件码，能识别多少算多少）、结果（成功/密码错误/次数用尽/过期）
- 支持导出 CSV（团队版）
- 默认只保留 90 天，后台可配置；IP 只存哈希或截断值，不展示原值

**实现要点**

- 事件不要写进 `metadata.shares` 的整包 JSON：每次访问都 CAS 落盘会放大写竞争。建议新增独立的 append-only 事件文件（如 `storage/analytics/share-events.jsonl`）或 MySQL 事件表，按天聚合后再读。
- 在分享页打开、密码校验成功、预览、下载、取件码查询这几个入口埋点；下载成功以服务端响应为准，避免前端误报。
- 聚合接口放在 `server/services/shares.js` 或新 `services/analytics.js`，管理页按 `manageToken` 鉴权。
- 前端在分享管理页加「数据」区块，复用现有卡片/进度条样式，不引入新图表库。

**验收标准**

- 同一设备多次刷新，UV 不重复膨胀；不同设备能区分。
- 访问/下载事件在 5 秒内可查；管理页接口 P95 < 300ms（1 万条事件以内）。
- 非资源所有者无法读取数据；公开分享页不泄露访问者信息。
- 关闭/过期分享仍能看到历史数据，但不再新增事件。

**风险**

- 隐私合规：访问日志属于个人信息，需在隐私政策中说明，并提供保留期限与删除机制。
- 误判：浏览器预取、爬虫、安全扫描会产生访问，需过滤已知 UA/IP 或标注「疑似机器人」。
- 数据膨胀：必须按天聚合 + 定期清理，不能无限追加。

### F2 收集任务 2.0

**用户故事**

> HR 用收集链接收简历，希望提交人必须填「姓名、手机号、应聘岗位、作品集链接」；有人提交后，HR 希望企业微信立刻收到提醒；老师收作业，希望有「作业提交」模板，不用每次从头设置。

**功能清单**

1. **自定义字段**
   - 字段类型：单行文本、多行文本、手机号、邮箱、下拉选择、单选、复选框、说明文字
   - 每个字段可设：必填/选填、占位提示、最大长度、选项
   - 收集创建页支持拖拽排序、预览
   - 提交页动态渲染；服务端校验必填、格式、长度
   - 管理页展示字段值；xlsx 清单按字段导出
2. **提交通知**
   - 新提交站内信通知收集人
   - 邮件通知（复用现有 SMTP）
   - 可选 IM 通知（为 F4 预留）
   - 支持「即时通知 / 每日汇总 / 关闭」
3. **场景模板**
   - 简历收集：姓名、手机号、邮箱、应聘岗位、作品集链接
   - 作业收集：姓名、学号、班级、作业说明
   - 合同收集：公司、联系人、合同编号、备注
   - 素材收集：品牌/项目、用途、版权说明
   - 活动照片：姓名、团队、照片说明
   - 模板只预填表单，创建后仍可改
4. **提交审核（可选二期）**
   - 提交状态：待审核 / 通过 / 驳回
   - 收集人可写审核备注；驳回可附原因
   - 支持按状态筛选、批量通过
   - 如提交人留了邮箱，可发送审核结果通知

**实现要点**

- 数据模型：`task.formFields = [{ id, label, type, required, options, placeholder, maxLength }]`；`submission.fields = { [fieldId]: value }`。
- 兼容旧任务：没有 `formFields` 时只显示「提交人名称」，不破坏现有提交。
- 字段值要限长、转义；手机号/邮箱做格式校验；xlsx 导出全部按文本写入，避免科学计数法。
- 通知复用 `services/account.js` 的站内信/邮件能力，新增 `collectionSubmitted` 事件类型，并接入通知偏好。
- 匿名提交涉及个人信息，提交页需加简短隐私说明和同意勾选；对同一 IP/设备做频率限制，必要时加验证码。

**验收标准**

- 创建一个含 5 个字段的收集任务，提交后管理页和 xlsx 都能看到完整字段值。
- 必填缺失、手机号/邮箱格式错误能被服务端拒绝，并给出字段级提示。
- 新提交后收集人在 1 分钟内收到站内信；配置 SMTP 后能收到邮件。
- 模板创建任务不超过 3 步；旧任务打开不报错。

**风险**

- 匿名收集 + 自定义字段会收集更多个人信息，需要隐私政策、同意勾选、保留期限。
- 恶意提交/垃圾提交：频率限制、单任务提交上限、必要时验证码。
- 字段过多导致移动端表单过长：限制字段数量（建议 ≤ 10），支持分组/说明。

### F3 品牌分享页 + 二维码海报 + 自定义短链

**用户故事**

> 设计公司给客户发方案，希望分享页有公司 logo、品牌色和一句欢迎语；婚礼/活动把二维码印在海报上，不希望是一个光秃秃的白底方码；企业希望链接是 `kunqiong.cn/s/abc` 而不是一长串随机字符。

**功能清单**

1. **品牌分享页**
   - 上传 logo（服务端用 `sharp` 压缩/裁剪，限制类型和大小）
   - 品牌主色、封面图、欢迎语、页脚说明
   - 分享页展示「由 XX 提供」；付费/企业版可移除平台标识
   - 个人会员可用「简洁封面 + 留言」，团队版可用完整品牌
2. **二维码海报**
   - 选择模板（简约/商务/活动/婚礼/招聘）
   - 自动填入标题、取件码、有效期、品牌 logo
   - 下载 PNG（1x/2x），支持复制图片
   - 海报上的二维码指向分享页，不直接暴露下载接口
3. **自定义短链**
   - 分享创建后可设置 ` /s/<slug> `，如 `/s/spring-campaign`
   - slug 全局唯一，保留词禁用（admin、api、share、collect、settings、workspace、team、auth、static 等）
   - 修改 slug 后旧链接保留 301 或同时可用（建议保留旧链接 30 天）
   - 团队版可绑定团队前缀，如 `/s/team-slug/xxx`；自定义域名放到企业版二期
4. **分享留言**
   - 发送方可写一段话，展示在分享页顶部
   - 支持「给收件人的话」和「下载说明」两个短文本

**实现要点**

- 品牌配置存在 `metadata.organizations[].branding` 或用户级 `branding`；分享页渲染时按 `teamResource`/owner 取品牌。
- 图片上传复用现有 multer + sharp，限制 2MB、JPG/PNG/WebP，服务端重新编码，防止 SVG/HTML 注入。
- 海报用前端 Canvas 生成，复用 `qrcode` 依赖；注意跨域图片和字体加载，生成失败要有降级（只复制链接）。
- 短链新增 `/s/:slug` 路由，放在分享路由之前还是之后要确认 Express 匹配顺序；slug 校验用 `^[a-z0-9-]{3,32}$`，避免与现有路由冲突。
- 品牌页只改展示层，不改变分享鉴权、密码、下载次数、定向收件人的服务端校验。

**验收标准**

- 上传 logo 后分享页 1 秒内展示；手机端不横向溢出。
- 海报 PNG 在微信/手机相册中清晰可扫；二维码内容与分享链接一致。
- 自定义短链创建后立即可访问；重复 slug 返回 409；保留词被拒绝。
- 关闭/过期分享的品牌页仍正确显示状态，不泄露文件。

**风险**

- 品牌图片可能包含违规内容：限制类型、服务端重编码、提供举报/下架机制。
- 短链可能被用于钓鱼/仿冒：保留词、黑名单、速率限制、到期回收；企业版才开放自定义域名。
- 海报模板需要设计资源；首期建议 3 个模板，不做自由拖拽编辑器。

### F4（可选）企业 IM 通知

**用户故事**

> 团队用企业微信办公，客户提交了文件，希望群里立刻收到一条卡片，点开就能看；不想每天登录网站刷新。

**功能清单**

- 团队设置里配置企业微信群机器人 / 钉钉机器人 / 飞书机器人 Webhook
- 支持「测试发送」、启用/停用、选择事件：
  - 新分享创建
  - 分享首次被下载
  - 收集任务有新提交
  - 分享/收集即将过期
  - 成员加入/退出（可选）
- 卡片内容：资源名称、文件数/大小、提交人、时间、直达链接；敏感信息可脱敏
- 发送失败重试 3 次，记录最近 20 条投递日志
- 只有团队所有者/管理员能配置，普通成员只能查看状态

**实现要点**

- 新增 `services/webhooks.js`：统一 POST、超时 5 秒、重试、签名、日志。
- **SSRF 防护**：只允许 `https://qyapi.weixin.qq.com/`、`https://oapi.dingtalk.com/`、`https://open.feishu.cn/` 等白名单域名；禁止内网 IP、重定向到内网、非 443 端口。
- 事件总线复用现有通知触发点；收集提交在 `publishCollectionSubmission` 成功后触发，避免文件还没落盘就通知。
- Webhook 密钥加密存储，接口返回只显示末四位；测试消息频率限制。
- 卡片模板按平台区分，内容长度截断，避免超长导致平台拒收。

**验收标准**

- 测试消息 10 秒内到达群；事件触发后 10 秒内收到卡片。
- 错误 Webhook 不影响主流程（异步、失败只记日志）。
- 非管理员不能修改 Webhook；日志不泄露完整 URL/密钥。
- 内网地址、非白名单域名被拒绝。

**风险**

- Webhook URL 泄露等于群消息权限泄露：加密存储、最小展示、可重置。
- 平台 API 变更/限流：做降级和重试，不阻塞上传/提交。
- 消息内容可能含文件名等敏感信息：默认只发标题和数量，详细内容点链接查看。

## 8. 风险与依赖

| 风险 | 影响 | 应对 |
|---|---|---|
| 访问日志涉及个人信息 | 合规风险 | IP 哈希/截断、保留期限、隐私政策、删除机制；只对资源所有者展示 |
| 事件写入放大元数据 | 性能下降、CAS 冲突 | 独立事件存储 + 按天聚合，不写整包 `metadata.json` |
| 自定义字段收集 PII | 合规与滥用 | 同意勾选、字段限长、频率限制、匿名提交验证码 |
| Webhook SSRF | 内网探测/数据外泄 | 域名白名单、禁止内网 IP/重定向、HTTPS、签名 |
| 在线解压 zip bomb | 磁盘/内存打满 | 限制条目数、解压后总大小、单文件大小、嵌套层数；流式处理 |
| 阅后即焚竞态 | 同一文件被多次下载 | 每分享锁 + 一次性 token + 原子消费；明确「打开即失效」提示 |
| 品牌/短链被滥用 | 钓鱼、仿冒 | 保留词、黑名单、举报下架、企业资质审核 |
| 第三方 IM/LLM 依赖 | 限流、变更、成本 | 异步重试、降级、额度控制、供应商备份 |
| 套餐权益复杂化 | 用户看不懂、客服成本 | 一张权益对比表、升级页明确标注、后台可配置 |
| 测试成本被低估 | 回归破坏 | 每个功能配 API + UI 回归；复用现有 `scripts/verify-*` 模式 |

**外部依赖**

- 邮件：现有 SMTP 已可用，需确认发送配额和到达率。
- 短信：现有腾讯云短信，需模板审核；验证取件功能上线前先确认模板。
- 企业微信/钉钉/飞书：群机器人 Webhook 不需要应用审核，适合首期；如果要发应用消息/小程序，需要企业资质和审核。
- 自定义域名：国内需要域名备案和证书管理，建议放到企业版二期。
- AI：需要确认模型供应商、数据是否出境、是否用于训练、按次成本。
