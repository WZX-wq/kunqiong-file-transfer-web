测试不包括跨机网络、真实 ClamAV 病毒引擎 CPU、MySQL/多实例、CDN、浏览器首屏或真实支付服务。文件扫描使用本机 INSTREAM 协议模拟器，传输和权限仍执行实际实现。16 MiB 文件不足以证明 500 MiB/5 GiB 场景容量。业务指标始终启用访问审计，诊断对照单独标注。压测副本保留在 C:\Users\admin\AppData\Local\Temp\kunqiong-performance-Xhjqe3。

复现：在项目根执行 node scripts/performance-load.mjs，可设置 PERFORMANCE_EVIDENCE_DIR 和 PERFORMANCE_STAGE_SECONDS。

瓶颈证据：正常 C30 阶段服务 CPU 约 99.6%（单核口径），事件循环 P95 3303.01 ms；同步 metadata 写入、备份及重命名耗时合计 0.00 秒，占该阶段 10.46 秒的一部分。118 次请求产生 0.00 MiB 写入和 0.00 MiB 备份复制，均为逻辑文件字节，不能当作物理磁盘流量。

正常进程 CPU profile 中，normalizeRecordDate 占 5.77%；writeFileUtf8、rename、writeFileSync、copyFile 四类帧合计 0.00%。这些是整个正常进程的活动采样比例，不是单一阶段的耗时比例。详细热点以结果 JSON 的 profiles 字段为准；日志及业务持久化是否分离，应结合当前版本代码确认。

建议按以下顺序优化，保留现有审计与权限校验：

1. 将审计从业务 metadata 分离，使用独立追加日志或审计表；若采用有界队列批量写入，明确容量、背压、失败重试和退出落盘策略，避免高风险操作日志丢失。
2. 只规范化新增审计条目，维护有序且有上限的记录；避免每个请求重新处理、排序全部历史日志。
3. 减少业务 metadata 的同步全量序列化与备份，评估增量持久化或可恢复的异步批量保存，同时保留原子提交、并发冲突处理和恢复能力。
4. 优化后在相同数据规模、启用审计及真实扫描引擎的环境复测，并增加跨机压力、长时间运行及 500 MiB/5 GiB 文件场景，再确定上线容量。

测量限制：健康检查和前端 HTML 基线各 5 秒，业务读取普通阶段 8 秒，最长阶段仅 30 秒；上传只有 13 个文件、下载只有 26 个文件，其分位数样本有限。RSS 每 100 ms 采样，表中峰值是观测值。测试启用了 CPU profiler 与指标采集；同机客户端也会竞争 CPU，健康检查基线客户端事件循环接近饱和。诊断复用正常测试后的存储，包含前序上传和审计变化，结束 metadata 约 0.69 MiB（正常 C30 结束约 0.64 MiB）；它用于定位瓶颈，吞吐提升倍数不能直接作为优化收益承诺。
