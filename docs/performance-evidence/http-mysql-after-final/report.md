4. 收集任务多人提交 40 人，返回 201 的 40 次、实际落库 40 条；创建接口限流校验 通过。

## 五、瓶颈分析

**1) DB 连接池 5 连接是首要约束。** C30 持续负载下连接池峰值已建连接 5/5，排队峰值 46（queueLimit=50）；全测试 503 响应共 0 次，集中在写入场景（见第 6 条）。并发从 C1 升到 C10 后吞吐即进入平台（C30/C50 不再提升、P95 随并发线性上升），属于典型的连接池排队：单个业务混合请求包含会话、账号、组织、资源分页、用量、通知等多段串行 SQL，请求会反复申请/释放连接，因此连接池先于 CPU 饱和。

**2) 按需 SQL 次数直接决定吞吐上限。** C30 混合读取平均 **21.5 条语句/请求**（其中 SELECT 20.39 条、Innodb 行读 730.81 行/请求），写入语句 1.11 条/请求。用 C1 阶段 P50 32.81 ms 除以每请求语句数得到单条语句约 1.53 ms，按 5 条连接估算纯 SQL 串行上限约 152 req/s，实测 C10≈48.46 req/s；剩余差距来自服务端单核 CPU（读取阶段单进程 CPU 已接近 100–110% 单核口径）、审计 flush 等待与同机客户端竞争。放大项是分页与组织图加载：这些查询结果集都很小，瓶颈在往返次数与连接争用，而不是单条 SQL 执行时间。

**3) 访问审计是固定但非主导的成本。** 关闭访问审计的 C30 对照：吞吐 41.02 → 49.42 req/s（1.2 倍），P95 1093.33 → 784.99 ms，Questions/请求 21.5 → 20.21。该差异与阶段间波动同量级（诊断阶段在持续阶段之后运行、缓存更热），不能单独归因；可以确定的是审计写入走同一连接池、每次 API 请求追加 1 条 INSERT（压测期间关系表 `kq_audit_log` 新增 842 行，抽查 50 个请求号全部命中），是每请求固定的额外往返。

**4) 加密/实体解码成本显著。** 正常进程 CPU profile 中与关系载荷解密、实体 hydrate/打包相关的帧（decodeProtected、createCipherBase、crypto/cipher update/final、request-store.hydrate、hydrateRows、normalized-codec、structuredClone）合计活跃采样约 **44.9%**。关系表把实体载荷整体加密（entity_payload_json）后按请求解密，并要为每次请求把行数据 hydrate/pack 成业务对象，这是 MySQL 模式相对 JSON 模式的额外 CPU 成本，也是读取吞吐上不去的原因之一。

**5) 分页取齐与团队视图。** 团队概览、收发记录、回收站等路由在 DB 模式按游标分页取数（默认 50 行），而 JSON 模式一次性从内存快照取全量；分页显著降低单次响应字节，但让“列表 + 计数 + 成员用量”页面变成多段串行 SQL，C50 时更容易在连接池排队。

**6) 写入路径并发不健壮（本次最重要的可靠性发现）。** 服务端日志出现 `ER_LOCK_DEADLOCK` 0 次、`CAPACITY_CHANGED` 32 次、`METADATA_WRITE_FAILED` 0 次。受影响场景：上传完成（16MiB分片上传 C1=0、16MiB分片上传 C4=0、16MiB分片上传 C8=0）、收集任务多人提交（0/40 次非 2xx）。写事务虽然通过 `kq_write_lock` 行锁做作用域串行，但并发团队写入仍会撞 InnoDB 死锁；服务端对死锁/容量冲突没有有界重试，直接把 503/409 返回客户端。收集阶段实际落库 40 条，而返回 201 的只有 40 条——说明部分事务已经提交、响应却是错误码，客户端无法据此判断是否需要重试，存在“假失败”语义。

**7) 传输链路未成为瓶颈。** 上传/下载阶段的限制来自 16 MiB 字节复制、SHA-256 校验与扫描协议传输，DB 只承担会话与资源元数据写入（上传完成时一次事务），C8 阶段吞吐仍受同机字节拷贝与磁盘约束。

**交叉验证（数据库层压测）：** 数据库层压测在同一隔离 MySQL 实例上独立复现了本条根因 —— 写路径的 `INSERT IGNORE INTO kq_write_lock` 与 `SELECT ... FOR UPDATE` 组合会产生共享锁→排他锁（S→X）升级，20 并发同 key 时约 75% 的事务死锁，与本报告服务端日志中的 `ER_LOCK_DEADLOCK` 以及 503 `METADATA_WRITE_FAILED` 现象吻合。详见 `docs/PERFORMANCE-数据库压测报告.md`（该报告给出可复现的代码级根因；本次按要求未修改 server 源码）。

本次同机对照中 **MySQL 模式反而更快**：持续 C30 11.99 → 41.02 req/s（3.42 倍），C50 11.34 → 49.59 req/s。原因在本机（Windows）的 JSON 基线受同步文件 I/O 与文件锁开销限制：其 CPU profile 热点为 open、unlink、link、normalizeRecordDate、readLocalMetadataRevision、writeBuffer，C10 以后吞吐只有约 11.99 请求/秒，延迟随并发急剧上升；MySQL 模式把这部分成本转移到数据库连接池排队（混合读取 P95 从 C1 的 63.71 ms 增长到 C50 的 1250.12 ms）。

**基线可比性提醒：** `docs/PERFORMANCE-本机压测报告.md` 的历史 JSON 基线（Linux 容器，C30≈36 请求/秒、关闭审计后≈2377 请求/秒）与本机 Windows 基线（C30≈11.99 请求/秒、关闭审计后≈12.87 请求/秒）差异很大：同一份代码在 Windows 上受文件锁（open/link/unlink）与同步落盘影响，审计开关的收益也被掩盖。因此“两种存储模式谁更快”强依赖宿主文件系统，不能把本机 JSON 基线当作生产容量基线。
另需说明：本次 JSON 基线复用仓库现有 `scripts/performance-load.mjs`，其上传校验仍按旧目录 `storage/files/<shareId>/` 读取落盘文件，而当前代码已改为 `storage/users/<owner>/` 布局，导致基线中 16MiB分片上传 C1（1 次）、16MiB分片上传 C4（4 次）、16MiB分片上传 C8（8 次） 被记为 ENOENT 失败（压测脚本侧校验失败，不是服务端上传失败）；基线上传吞吐数字不可用，读取与下载数字不受影响。按要求未修改 server 源码迁就脚本。
基线数据规模：20 用户 / 201 分享 / 400 记录 / 5000 审计；本次 MySQL 数据规模见第二节，两者量级一致，差异不应归因于数据量。

## 九、建议

1. 连接池容量与排队：当前 connectionLimit=5 在 C30 已出现排队峰值 46、503 0 次。建议按目标并发做压测标定（例如 C50 目标下将 connectionLimit 提升到并发读请求数的一个分数，并同步调大 queueLimit / acquireTimeout），或按请求合并按需查询（一次请求内的会话 + 账号 + 组织 + 用量允许复用一个连接）。
2. 减少按需 SQL 往返：把同一请求内的多次 `store.config()/session()/account()/organizationGraph()/loadUsage()` 合并到单连接上的批量语句（multi-statement 或一次 JOIN），并缓存只读系统配置与套餐快照，避免每次请求重复读取。
3. 审计写入与保留：DB 模式访问审计已写入关系表 `kq_audit_log`（抽查全部命中），但保留上限 5000 未在写入路径裁剪（本次已到 5842 行）。建议补充基于时间的清理任务（服务启动路径明确调度审计 purge）并监控表增长，避免审计表随请求量无界膨胀。
4. 审计写入成本归因：关闭访问审计后 C30 吞吐从 41.02 提升到 49.42 req/s，差异与阶段间噪声同量级，说明访问审计不是主导成本（主要成本是连接池排队与按需 SQL）。仍建议把每请求 1 次独立 INSERT 改为有界队列批量提交（明确容量、背压、失败重试与退出落盘），以减少往返并把审计写入从响应路径移出。
5. 资源与文件元数据分页：继续沿用当前分页读取，避免一次请求解密大量 `entity_payload_json`；列表接口只返回必要字段，成员用量等聚合查询走 `kq_resource_usage` 预聚合表（当前已由迁移回填）。
6. 加密载荷成本：`entity_payload_json` 整体加密带来按请求 AES-GCM 开销，建议对非敏感的大字段（展示名、标题、时间等）保持明文列，仅对凭据/参与者信息加密，减少解密字节量。
7. 上线容量确认：本次只覆盖 16 MiB 文件、20 用户/201 资源的本机回环场景；真实部署还需跨机网络、长时间运行、500 MiB/5 GiB 大文件、真实 ClamAV 及多实例共享同一 MySQL 的场景复测后再定容量。

## 十、测量限制

- 健康检查与前端页面基线各 5 秒，业务读取普通阶段 8 秒、持续阶段 30 秒；上传仅 13 个文件、下载仅 26 个文件，分位数样本有限，不能外推为长稳结论。
- 压测客户端与被测服务、MySQL 容器、扫描模拟器同机运行，客户端事件循环与 CPU 会和被测服务竞争；表中“服务 CPU”是单进程 cpuUsage 增量按阶段时长折算的单核百分比口径。
- 扫描链路使用本机 INSTREAM 协议模拟器（required 模式），只验证协议往返与字节计数，不代表真实 ClamAV 病毒库扫描耗时。
- MySQL 全局状态增量包含服务端关系维护定时器（清理/对账/审计清扫）在窗口内的少量查询、以及每次快照自身 1 条 SHOW GLOBAL STATUS（已在 Questions 中扣除 1），阶段内业务查询占绝大多数；连接池排队为 20 ms 采样峰值，可能低估极短尖峰。
- 数据量小（约 200 资源 / 5000 条种子审计 / 数百 KB 载荷），InnoDB Buffer Pool 命中率全程 100%，本次没有测到磁盘 I/O 压力；真实数据量下缓冲池未命中与磁盘延迟会成为新的瓶颈。
- 连接池固定 5 连接（KUNQIONG_DB_CONNECTION_LIMIT=5），未做多档容量扫描；C50 的结果不能代表提高连接池后的表现。
- 收集提交阶段每位提交者上传 1 KiB 文本，主持人（企业权益）参与人数上限为不限，故未触发人数上限；限流校验按 5 分钟窗口 / 60 次与进程内已用额度动态计算期望值。
- 审计持久化结论：DB 模式访问审计写入关系表 kq_audit_log（RelationalAuditStore 覆写 insert），legacy 表 kunqiong_audit_log 不参与；本次以请求号抽查方式验证，未逐条核对全部请求。
- 收集提交与上传完成阶段的失败同时包含 503（服务端写事务失败/死锁）与 409（乐观并发冲突）；压测客户端不做自动重试，因此这些失败反映“一次尝试”的结果，不代表业务最终成功率，也说明客户端缺乏可判定的重试语义。
- CPU profile 在压测期间持续采样（约 1 ms 周期），会带来少量固定开销；profile 帧占比是整个进程的活跃采样比例，不是单阶段耗时比例。
- 多轮重复性：本次共完成 1 轮完整的 MySQL 模式压测（同脚本、同隔离库规格），业务读取持续 C30 阶段分别约 41.02 req/s，轮次差异约 ±35%（最高约为最低的 1.5 倍）；波动来自同机 Windows 桌面环境的后台 CPU 占用（20–30%）、共享 MySQL 容器的 4 CPU/3 GiB 配额与同机压测客户端竞争。最后一轮被用作本报告主数据，读者不应把单轮结果视为唯一可复现值。逐轮记录见第三节与证据目录 `repeat-runs.json`。
