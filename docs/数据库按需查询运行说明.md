# 数据库按需查询运行说明

启用 `KUNQIONG_DB_ENABLED=true` 后，HTTP 启动只初始化请求仓库，不连接数据库、不读取 `storage/metadata.json`、不查询 `kunqiong_app_state`，也不把整库业务数据加载到进程里。首页、静态文件和存活探针独立于数据库业务请求。

## 读写边界

- 登录按会话摘要及账号查询；收发记录、消息、订单按当前账号查询。
- 分享、收集、续传按资源标识或令牌查询；团队功能按当前团队查询。管理员总览仅在通过管理员认证、打开对应功能后读取管理域。
- 空间用量与进行中的收集数量使用 SQL 汇总。上传会话按 ID 从数据库恢复，分片字节及进度标记仍保存在文件系统。
- 每个请求独立保存已加载数据及改动基线。事务只更新或删除本次明确修改的实体和其子记录，不将未加载数据视为删除。
- 使用账号、团队、资源及磁盘键的事务锁，不再用一把全局 revision 锁串行处理所有用户。提交前复查会话、账号与团队权限；同一实体的冲突修改返回 `409`，不同提交人的收集子记录可合并，并在锁内重新检查参与人数及空间上限。
- 消息、记录、团队文件及回收站接口使用 ID 游标分页，默认 50 条、上限 200 条。管理员统计使用 SQL 聚合，列表只取 200 条投影，审计展示只取 100 条。
- 后台清理按游标分批查询；不在启动阶段扫描全部资源、上传会话和审计历史。

用户、资源、文件、提交、团队成员及分发映射从关系列及子表还原，资源扩展不再重复保存完整文件/提交数组。加密扩展保留未单独建列的属性和字段存在标记；套餐、设置等配置 JSON，以及账号记录的历史展示快照仍保留。它们只随选中的记录读取，不作为整库 JSON 快照读取。未启用数据库的单机文件模式继续兼容原有存储。

当前客户端为兼容原有筛选与列表交互，会在打开列表后逐页取齐；单个收集任务的业务接口仍按任务还原子记录。服务启动不会加载这些数据，但这不等于所有大列表已经采用滚动加载或虚拟列表。

## 文件与事务

删除已发布文件时，在业务 SQL 事务中写入 `kq_file_cleanup`，事务成功后再删除字节。业务回滚不会提前删文件；重启后可继续处理已提交任务，文件系统错误会记录错误码并退避重试。孤立文件扫描会直接查询 SQL 引用，执行删除前再次在对应资源/磁盘键锁下确认引用，避免将本次未加载的数据误判为孤立。

## 连接配置

连接池按需建立连接，默认最多 5 个连接、排队 50 个请求、获取连接等待 30 秒、单次查询或事务确认等待 60 秒。超时会释放迟到连接或销毁失效连接，业务接口返回可重试错误；这些限制用于用户请求，不是 HTTP 启动前检查。

可配置 `KUNQIONG_DB_CONNECTION_LIMIT`、`KUNQIONG_DB_QUEUE_LIMIT`、`KUNQIONG_DB_CONNECT_TIMEOUT_MS`、`KUNQIONG_DB_ACQUIRE_TIMEOUT_MS`、`KUNQIONG_DB_QUERY_TIMEOUT_MS`。`KUNQIONG_DB_TLS=true` 启用证书校验的 TLS；服务端证书须受运行环境信任。新连接统一使用 UTC 会话时区。发布脚本会继承并校验这些配置。

## 首次升级

适用于已经完成关系表业务数据迁移，并已存在 `kq_relational_store_state`、上传会话表和关系审计表的数据库。未迁移的旧库需先单独完成基础结构与历史业务迁移；HTTP 服务不会自动导入或回退读取本地 JSON。

1. 使用与运行容器相同的数据库配置和 `KUNQIONG_DATA_KEY`，备份数据库并停止旧版本写入。
2. 在新代码目录执行 `npm run db:on-demand:apply`，或在新镜像中执行 `node scripts/db/migrate-on-demand.mjs --apply`。
3. 成功后启动新版本。

迁移 `005-on-demand-resource-usage` 新增资源用量及上传发布索引表，从现有关系记录按每批 50 条回填。它不读取本地 JSON，不删除现有业务表。已执行同版本迁移时仅核对迁移版本后退出，不重复回填。

迁移 `006-normalized-entities-and-cleanup` 增加写版本、局部事务锁、清理队列、文件路径摘要和分页索引，并将已有实体转换为关系列与子表读取，最终设置 `schema_version=3`。转换按聚合分别提交，已转换记录跳过；中断后可以用同一命令继续。迁移登记校验覆盖列、索引及新增表定义，迁移期间必须停止其他版本写入。

`scripts/deploy-test.sh` 已将此命令接入备份后的发布步骤，运行镜像包含迁移脚本与 `mariadb-dump`。应用容器名继续使用 `kunqiong-file-transfer-web`，测试服自动停机策略保持原样。

## 备份与恢复

发布在停止旧 writer 后，先用一致性事务、流式输出生成 `mysql.sql.gz`，再写包含 SHA256 的 `mysql-backup-complete.json`；备份失败会中止发布，不更新最近成功备份指针。数据库账号需要相应表、触发器、例程及事件的导出权限。备份目录还保存旧配置、镜像标识及存储卷中的保护密钥/旧元数据/审计文件。上传文件继续保留在原卷，发布备份不等于上传文件的独立灾备副本。

恢复时停止相关 writer，核对压缩文件 SHA256 与完成标志，将 SQL 导入另一个空数据库，使用匹配的 `KUNQIONG_DATA_KEY` 和上传文件卷验证，再切换数据库配置。若需要回滚到旧代码，必须同时恢复升级前匹配的数据库备份及密钥；旧代码不能直接向已转换的 schema 3 数据写入。迁移登记、用量及清理队列表应来自同一份备份，不要单独删表或混用密钥。

## 本地验证

`npm run test:db-on-demand` 包含独立 MySQL 集成测试及启动生命周期测试。集成测试需显式设置 `KUNQIONG_TEST_DB_PORT`，只连接 `127.0.0.1` 的临时测试实例，并创建、删除随机的 `kunqiong_demand_test_*` 测试库；不继承项目生产数据库配置。

已验证本地 JSON 损坏时仍可启动、数据库握手卡住时首页与健康探针可用、连接/查询挂起、独立账号并发、同任务并发及配额竞争、回滚保留文件、清理任务恢复重试、孤立文件二次保护、迁移中断重试、125 条消息分页与批量操作、管理员跨批清理、真实 SQL 备份恢复、分片续传重启、收集、团队及 OAuth 登录。真实备份恢复测试使用本机 MySQL 工具；Docker 镜像内的 MariaDB 导出工具需在实际发布环境验证。

公网链路偶发返回延迟时，非锁定只读查询允许销毁旧连接后重试一次，两次共用同一个等待预算。单条写入语句不会因网络超时自动重放；尚未发送 COMMIT 的业务事务可销毁连接、由 MySQL 回滚后，在新连接上整体重试一次。COMMIT 已发出而确认丢失时不重试，按提交结果不确定处理。用户、组织、订单和消息按请求读取，并逐次以 MySQL 版本字段校验有界内存缓存；数据库失败时不返回过期缓存。

首次握手在 SQL 发出前失败时，可在同一连接等待预算内重建连接一次；事务连接不单独重放失败语句。公网查询默认 60 秒，连接等待默认 30 秒；每个应用连接的 MySQL 会话执行上限也同步为该配置值；不修改数据库 GLOBAL 上限。

版本缓存最多 512 行、8 MiB；每次仍先按原有 SQL 权限条件核对版本，不在数据库失败时回退。冷读取按估算 32 KiB 分批，超出一批的单条实体独立读取；分页游标和数量不变。
