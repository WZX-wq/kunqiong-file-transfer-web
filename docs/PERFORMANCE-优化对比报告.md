# 性能瓶颈优化与复测

完成时间：2026/10/12 14:13:10（Asia/Shanghai）。本机 JSON 模式的业务读取瓶颈已改善，访问审计始终启用。30 并发吞吐提升 11.20 倍，50 并发 P95 从 1379.26 ms 降到 128.74 ms。全部读取阶段达到本次 P95 ≤ 500 ms 参考目标，非预期错误为 0；这不是线上容量承诺。

## 改动

访问审计改为 storage/audit/snapshot.json 与 events.jsonl 独立存储。每个请求只规范化并追加新条目，不再重新规范化全部历史日志或触发整份业务 metadata.json 保存与备份。内存保留最多 5000 条日志，日志每 1000 次追加或达到 8 MiB 时生成快照并轮换。

历史审计在启动时迁移并立即保存迁移标记；业务修改仍保留原有原子文件替换、备份、版本与冲突合并。业务快照标记 auditStorage=journal-v1，后续保存不重复内嵌审计。后台统计和保留期清理读取独立日志，多个进程写入通过发布完整所有权标记的文件锁串行处理。

审计快照保存日志代次与已应用字节位置，防止轮换中断后重新加入已清理的条目。启动可用备份恢复损坏快照，修复中断写入的末尾半行；完整行损坏或已迁移存储丢失会明确报错。普通访问写入关闭文件后由操作系统缓存持久化，不能承诺断电前全部落盘；管理与安全事件追加后执行 fsync。访问日志写入失败会输出含请求 ID 的 audit_write_failed 运维事件，并保持只读服务可用；磁盘故障期间该访问记录不会伪称已写入审计文件。

解耦后补齐了文件清理、团队解散的明确业务保存，并处理 Windows 下同时删除同一团队资源时可能出现的 EPERM。权限判断保持服务端实时校验，未降低登录、容量、扫描或限流要求。
