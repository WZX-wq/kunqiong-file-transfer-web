## 当前与拟议的区别

2026-10-29 本机 MySQL 8.0.41 当前共 26 张物理表：21 张关系业务/审计表、1 张上传会话表、2 张迁移/状态基础表，并保留 `kunqiong_app_state` 与 `kunqiong_audit_log` 两张兼容表。业务读写已切换到关系存储；正常保存使用 revision 绑定的进程内缓存并按变化实体同步，审计表保留双写兼容。上传续传清单加密后写入 `kq_upload_session`；文件分片仍在磁盘。5,000 条合成用户容量烟测、事务回滚和隔离库备份恢复结果见 `01-当前实际数据库说明.md`。这些本机测试不等于生产容量、持续并发或生产备份介质演练。

隔离备份恢复测试需要本地 MySQL 管理账号临时设置 `KQ_TEST_DB_ADMIN_USER` 和 `KQ_TEST_DB_ADMIN_PASSWORD`；应用 `.env` 继续使用受限账号，管理员凭据不写入项目配置。

44 张是全量目标关系模型，包含账号、组织、订单等已有实体的规范化，以及 v4 各阶段扩展；不是首期必须一次建完，也不是当前已存在 44 张表。保留既有审计表后目标表数还会另计 1 张；过渡期可能继续保留快照表。生产迁移应逐域实施。

如果只评审当前已完成的能力，请以 `03-现有功能关系表设计.md` 和对应 SQL 为准。该 21 张业务表方案排除了尚未实现的 v4 扩展；它仍是目标模型，不是当前线上/本地实际表结构。

## SQL 使用边界

- 使用 MySQL 8.0.16+；实际结构验证采用 MySQL Community 8.0.41 的隔离临时实例。
- 拟议 SQL 包含 CREATE TABLE 和 ALTER TABLE ADD FOREIGN KEY，不创建/切换数据库，不写入数据，不删除现有表；必须在专门创建的空白测试库执行。
- `03-现有功能关系表设计.sql` 是运行关系模型使用的业务表 DDL；服务启用关系模式时执行增量结构迁移，并在首次启动时回填快照。
- `npm run db:schema:check` 可本地静态检查；`npm run db:schema:apply` 是显式建表命令，创建关系表与迁移版本控制表，但不回填业务数据或切换应用读写。
- 配置 `KUNQIONG_RELATIONAL_SCHEMA_ENABLED=true` 可让服务启动时执行同一版本化结构升级；默认关闭，避免未确认数据库目标时自动建表。
- `db:schema:apply` 仍只建表/核对结构，不回填数据；首次数据回填由启用关系模式的服务启动流程完成。
- 本机关系切换已用事务试写回滚和完整快照往返校验；快照与审计旧表仍保留。生产部署仍需单独安排停写、备份、文件引用核对、容量压测和恢复演练。
- 不要将 current 与 proposed 理解为可以直接顺序升级的 migration；v4 扩展仍需另行设计和实施。
- 核对不读取业务记录、`.env`、连接密码或真实令牌；测试仅写入隔离库的合成数据，完成后关闭并删除临时实例。

## 状态边界

安全扫描 `reviewStatus` 与业务验收分开。普通二维码与同一草稿跨设备接力分开。下载事件与主动确认分开。本地浏览器模板与云端模板库分开。当前批量分发要求匹配已有账号，外部验证领取属于扩展。

两份文档均以 2026-10-29 的源码为现状基线；v4 范围来自仓库现存 `docs/新功能规划.html` 的 22 项需求，保留电脑与手机网页方案。
