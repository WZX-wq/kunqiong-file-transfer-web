## 二、【核心 Bug】加入团队导致个人套餐被误提升为企业版

### 根因
`accountEffectivePlanForUser` 原文：

```js
const directPlan = accountPlanForUser(directUser)
if (directPlan.id !== 'free') return directPlan
const organization = accountOrganizationForUser(userId)
if (organization && organization.ownerUserId !== userId) {
  return accountPlanForUser(accountUserById(organization.ownerUserId) || {})  // ← 直接套用所有者套餐
}
```

**个人是 free（基础版）时，一旦加入别人（企业版所有者）的团队，整个函数直接返回所有者的企业版套餐。**
后果远不止"显示错"：

| 受影响面 | 错误表现 |
|---|---|
| 个人空间容量 | 20GB → 误显示 2048GB（`accountUsageForUser` 用它算 totalBytes） |
| 永久保存 | 基础版本不支持，却被误开（`permanent: true`） |
| 分享有效期 | `readShareOptions` 允许设"永久保存"；`share.expiresAt` 逻辑全部走永久分支 |
| 重新打开分享 | `payload.canReopen` 被误设为 true |
| 永久保存徽标 | `plan.permanent` 驱动 UI 显示"支持永久保存" |
| 后台用户列表 | `adminUserSummary` 用 effective → 该用户在企业版团队里显示"企业版" |
| 升级下单 | `POST /api/account/upgrade-orders` 的等级比较用 effective → **基础版成员想购买会员版会被误判"当前已享有企业版权益"而拒绝** |

### 修复方案：个人套餐与团队权益彻底分离
拆成三个函数，语义清晰：

```js
// 个人套餐：只看 user.planId，与团队归属无关。个人空间/永久保存/单文件上限的唯一依据。
function accountPersonalPlanForUser(user) { return accountPlanForUser(directUser) }

// 团队权益：借用团队的**团队侧**能力（仅 teamSpaceBytes / team 开关）
function accountTeamEntitlementForUser(user) {
  const personal = accountPersonalPlanForUser(user)
  const organization = accountOrganizationForUser(userId)
  if (!organization) return personal
  if (organization.ownerUserId === userId) return personal          // 所有者：自己的套餐即团队权益
  const ownerPlan = accountPersonalPlanForUser(accountUserById(organization.ownerUserId) || {})
  if (!ownerPlan.team) return personal
  return { ...personal, team: true, teamSpaceBytes: Number(ownerPlan.teamSpaceBytes || 0) }
  // ⚠️ 关键：只覆盖 team/teamSpaceBytes，totalBytes / permanent / label 全部保留成员自己的
}

function accountEffectivePlanForUser(user) { return accountTeamEntitlementForUser(user) }  // 保留名字，兼容既有调用
function organizationTeamSpaceBytes(organization) { /* 唯一来源：所有者套餐 */ }
```

### 逐处调整调用点（用 personal 而非 effective）
- `accountUsageForUser` → **personal**（个人容量必须按自己算）
- `accountTeamUsageForOrganization` → **personal**（团队空间属于所有者）
- `adminUserSummary` → **personal**，并新增 `organizationRole` 字段（owner/member）
- `accountWorkspacePayload` → plan 改 **personal**，新增 `teamEntitlement` 块
- `publicAccountUser` → plan 改 **personal**，新增 `teamEntitlement` 块
- `accountBenefitsForUser` → 成员视角改文案为「已加入「X」，共享其团队空间容量」，不再宣称个人升级

> 保留 `accountEffectivePlanForUser` 这个名字，是因为 `.team` / `.permanent` 的既有判定语义仍正确
> （`.permanent` 现在取自个人套餐，正是我们想要的）。这样改动面最小、回归风险最低。

### 前端配套（src/main.jsx）

- **修掉一个连带缺陷**：团队状态标签原先恒显示「团队所有者」，成员也显示所有者 → 改为按 `role` 显示「团队成员」

## 三、后台管理安全审计（发现 3 个真 Bug）

### Bug 1（严重）：删除资源抛 ReferenceError，资源已删但报 500 且审计丢失
`DELETE /api/admin/resources/:kind/:id` 末尾写的是 `userId: session.user.id`，
但**该作用域内没有 `session`**（认证变量叫 `auth`）。资源先被 `splice` 掉，随后记录审计时抛错 →
**接口 500、资源已不可恢复、审计日志没写**（等于删了但没留痕）。
修复：改为 `auth.user.id`。

### Bug 2：自禁用保护恒为 false，形同虚设
```js
if (user.id === auth.user.id && status === 'disabled')  // auth.user.id = "admin:ljxkjadmin"
```
`auth.user.id` 是 `admin:<账号名>` 形式，与鲲穹账号 id 永远不相等 → 这个保护从来没生效过。
修复：解析出账号名再比对：
```js
const adminUsername = String(auth.user.id || '').replace(/^admin:/, '')
const isSelfAccount = adminUsername && (user.username === adminUsername || user.id === adminUsername)
```

### Bug 3（严重）：后台登录限流可被伪造 X-Forwarded-For 绕过
`app.set('trust proxy', true)` + `clientIpFromRequest` 直接读 XFF 作为限流键。
攻击者每次请求换一个伪造 XFF 值，就能把计数摊到无数个"IP"上 →
**8 次/10 分钟的限流完全失效，等于对 12 小时有效期的口令登录开放无限次暴力破解**。
修复：改用 `adminRateLimitKeys(req)` 返回多个键，任一超限即拦截：
```js
function adminRateLimitKeys(req) {
  const socketIp = String(req.socket?.remoteAddress || '').trim()   // 真实 socket 地址
  const proxyIp = clientIpFromRequest(req)
  const keys = [`socket:${socketIp || 'unknown'}`]
  if (proxyIp && proxyIp !== socketIp) keys.push(`proxy:${proxyIp}`)
  keys.push('global')   // 全局兜底桶，伪造头也无法完全敞开
  return keys
}
// 全局桶额度放宽 ×6，避免正常用户被少量失败拖累
```
三个函数签名从 `(ip)` 改为 `(req)`，`/api/admin/login` 调用点同步更新。

## 五、本轮踩到的环境坑（重要，可复用）

### 1. `cpSync(目录, 目录, {recursive:true})` 会**静默杀进程**（exit 127 且零输出）
在沙箱里复制 `dist/` 时踩到，脚本在第 6 步直接死掉，任何日志都没写。
→ 必须**逐文件复制**（自写 `copyTree` 递归）。这是 `_verify_member_ui.mjs` 一开始"零输出"的真因。
排查手法：用 `fs.appendFileSync` 分步写日志定位到具体语句（我一开始误以为是 `spawn` 不可用，
实测 `spawn` 单独跑 Chrome **完全正常** —— 别凭直觉归因）。

### 2. `server.mjs` **不导出 app**，靠 side effect 自行 listen
`Object.keys(mod)` 为空 → `mod.default || mod.server || mod.app` 全是 undefined，
再调 `server.listen()` 就抛错。正确做法：设好 `process.env.PORT` 后直接 `await import(...)`，
然后轮询 `/api/health` 等端口可达。**不要在脚本里自己 listen。**

### 3. 断言里的单位算错会造成假失败
企业版 `teamSpaceBytes` 在代码里是 `1024 * 1024 * 1024 * 1024`（GiB 写法），
我第一次写成 `1024 ** 3`，实际返回 1099511627776 是**正确的**，却被判 FAIL。
→ 断言期望值时照抄 `server.mjs` 里的表达式，别自己换算。

### 4. 测试顺序会互相污染（限流类）
`_verify_admin_audit.mjs` 第一版把"空账号密码 → 400"放在限流测试之后，
限流已在 20 次失败后耗尽额度，导致空参数请求先被 429 抢答 → 假失败。
→ **会消耗配额/改变状态的用例必须放最后**，校验类放前面。

## 六、第二轮任务：自定义头像在重启/重新登录后丢失（已修复并部署）

用户需求原文：
> 那个个人头像上传了，是不是不能正常保存头像，我之前上传过，这次再登录就没了

### 定位过程（关键：先用测试证明"现有链路是对的"，再往上游找）

第一层 `_verify_avatar.mjs`（14/14 全绿）：保存 → 落盘 → `/api/auth/me` → 模拟重登合并，
**整条链路完全正确**。说明问题不在保存逻辑，而在**别的地方**。

第二层 `_verify_avatar_restart.mjs`：直接从 `server.mjs` 用大括号配平**抽取真实函数**
（`publicUser` / `normalizeAccountUser` / `mergeAccountUser` / `normalizeAccountUserStore`）
拼成临时模块来跑，避免"复刻逻辑"引入偏差。一跑就复现了：

```
场景 B：会话快照缺失 avatarSource（历史会话/旧数据）
  结果：avatarSource="" avatar=https://provider.example.com/avatar.png   ← 自定义头像没了
```

### 根因：两个缺陷叠加

**缺陷 1（主因）** — `mergeAccountUser` 判断"用户是否对头像表态"，用的是
`avatarSourceExplicit = hasOwnProperty(incoming,'avatarSource')`（**有没有这个键**）。
但 OAuth 登录快照、会话快照、后台改库都会带一个**显式 `avatarSource: ''`**，
于是 `normalizeAccountUserStore` 在**每次重启**把 `metadata.sessions[].user` 合并回用户表时，
把已存的 `avatarSource:'custom'` 覆盖成 `''`，头像随之被重算成 provider 头像。
→ 这正是"上传过、下次登录就没了"。

**缺陷 2（隐藏得更深，最先把我卡住）** — `upsertAccountUser` 写的是：
```js
const normalized = normalizeAccountUser(user)                                  // ← 只输出持久化字段
metadata.users[normalized.id] = mergeAccountUser(metadata.users[normalized.id], normalized)
```
`normalizeAccountUser` 只返回白名单字段，会把 `avatarRestoreRequested` 这类**意图标记吞掉**。
我加了插桩才看清：调用方明明传了 `avatarRestoreRequested: true`，进到 `mergeAccountUser` 里
却变成 `undefined`。**中间隔了一层归一化**。
> 教训：给合并函数传参时，别先过一遍"字段白名单"再传，否则任何非持久化的意图标记都会丢。

### 修复方案：自定义头像改成「粘性」字段 + 显式意图标记

```js
// mergeAccountUser 内
const restoreRequested = incoming.avatarRestoreRequested === true   // 只有显式标记才允许清除
const nextAvatarSource = normalized.avatarSource === 'custom'
  ? 'custom'
  : base.avatarSource === 'custom' && !restoreRequested
    ? 'custom'          // ← 粘住：普通快照改不动它
    : ''
```
- **不能用 `avatar === null` 判断"恢复登录头像"**：恢复时 `avatar` 会被填成 provider 地址，不是 null。
  必须由调用方显式打标记 `avatarRestoreRequested`。
- 标记在合并末尾 `delete merged.avatarRestoreRequested`，**绝不落库/下发**。
- `upsertAccountUser` 与 `normalizeAccountUserStore` 改为传**原始输入**给 `mergeAccountUser`。
- `mergeAccountUser` 去掉 `if (!existing) return normalizeAccountUser(incoming)` 短路
  （首条记录也要走完整合并，否则首次操作丢标记）。
- `PATCH /api/auth/profile` 与 `POST /api/account/bind` 改为以**用户表**（而非 `session.user` 快照）为准合并：
  快照可能过期（另一台设备刚改过），整体覆盖会造成"保存昵称顺手把头像改没了"。

### 本轮新增环境坑
- **`fs.symlinkSync(..., 'junction')` 建立 `node_modules` 链接是可行且快速的**（780MB 目录秒建），
  比 `copyTree` 快几个数量级，适合沙箱化真实 server。
- 但**建完 junction 之后脚本仍可能被杀**：本次真因是先前 `rmSync(SANDBOX)` 清理旧沙箱耗时过长（约 87s）
  触发工具超时，而非 curl/junction。定位手段仍是**分步 `trace()` 写文件**，别靠猜。
- 抽取函数做单测时，`src.indexOf('function name(')` 只会命中**声明行**；
  真实签名常跨行（`function f(a = {}) {` 里 `{` 在下一行），
  → 正确做法：先找 `'\nfunction name('`，再 `indexOf(')')` 定位签名末尾，然后从签名末尾往后找第一个 `{` 开始配平。
